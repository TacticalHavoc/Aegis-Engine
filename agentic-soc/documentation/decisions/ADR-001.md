# ADR-001: REST API Boundary for Alert Ingestion

Status: Accepted

## Context

The overall system architecture involves endpoint log forwarders streaming events into Kafka, followed by centralized log processing and a hybrid detection engine (rule-based + ML). The detection engine generates security alerts that must be ingested by the Agentic SOC for investigation and triage.

We needed to decide how the Agentic SOC should interface with the upstream detection pipeline: whether to embed a Kafka consumer directly within the agentic application or to expose an explicit HTTP REST API boundary.

## Decision

We decided to establish an explicit REST API boundary (`POST /api/v1/alerts`) as the ingress interface for the Agentic SOC.

During development, alerts can be submitted directly via Postman, test scripts, or curl. When upstream detection systems and Kafka are fully deployed, a lightweight Kafka consumer will read alerts from the detection topic and POST them to this REST API endpoint.

## Alternatives Considered

1. **Embedded Kafka Consumer Inside Agentic SOC**:
   - Directly running an `aiokafka` consumer loop inside the agent framework.
   - *Drawbacks*: Tightly couples the agentic codebase to Kafka broker infrastructure, consumer group state management, and network availability during local agent development and testing.
2. **Direct Shared Database Ingestion**:
   - Having the detection engine write alerts to a shared database and having the agent service poll or listen to database triggers.
   - *Drawbacks*: Creates tight schema coupling at the database level and obscures service ownership.

## Rationale

- **Decoupling**: The Agentic SOC remains producer-agnostic. It treats alerts from Postman, synthetic test runners, or production Kafka consumers identically.
- **Independent Development**: The agentic investigation subsystem can be developed, tested, and iterated on independently without requiring active Kafka brokers or teammates' pipelines.
- **Fail-Fast Validation**: Incoming alerts are strictly validated at the API boundary using Pydantic before any downstream resources or LLM contexts are engaged.
- **Asynchronous Acceptance**: Responding with `202 Accepted` acknowledges receipt immediately, preventing HTTP timeouts that would occur during long-running multi-turn agent investigations.

## Consequences

- Upstream pipelines require an adapter or forwarder (e.g., a lightweight Kafka consumer service) to push alerts to the REST endpoint.
- Alert queueing and persistent backlog buffering must eventually be addressed (either via background task queues or message brokers) in downstream service milestones.
